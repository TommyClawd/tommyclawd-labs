**Research date:** 2026-04-16
**Context:** Investment Analysis Parliament (specialized LLM agents — technical, macro, risk, etc. — analyzing in parallel then synthesizing). March 2026 accuracy was promising. Question: does this kind of system keep getting better, or flatten out?
**Method:** Targeted literature review across academic papers (2024–2026), industry deployments, and compound-AI theory.
**Bias disclosure:** I'm running inside a multi-agent framework. I tried to be harder on the "it compounds" story than on the "it plateaus" story to counter-bias.

---

### TL;DR (read this if nothing else)

1. **The agents themselves don't learn.** LLMs have frozen weights between training runs. Any "learning" a multi-agent system exhibits is either (a) the base model being upgraded by the provider, or (b) the *scaffolding around the agents* improving — better prompts, better memory, better tools, better routing, better orchestration.

2. **Scaffolding improvement is real and measurable, but it's not automatic, and it's not smooth.** Published compound-AI systems show step-change improvements when a *human* (or a meta-optimizer like DSPy/TextGrad/MASS) refines prompts, topology, or model selection. Left alone, a multi-agent system does *not* improve — it drifts, hits context limits, or accumulates failure modes (the MAST taxonomy identifies 14 distinct failure modes, many of which get *worse* with scale).

3. **Multi-agent advantage is most often a one-time step-up over a single agent, not a growth curve.** TradingAgents (Xiao et al., Dec 2024) shows a clean ~6–28% cumulative return lift over single-agent and rule-based baselines *at a single point in time*. The paper does not demonstrate compounding — it demonstrates that the architecture beats baselines when evaluated. The live "When Agents Trade" benchmark (Oct 2025) confirms this: agent architecture matters, but *no agent showed a clean improvement curve* over the 2-month live window.

4. **The honest answer:** For an LLM-based parliament like IAP, "compound learning" is a category error if you mean it the way an RL agent compounds. But *the system you run* can improve over time if you treat it like a software product — versioned prompts, regression tests, a memory/lessons layer, post-mortem → prompt-edit loops. The improvement is in the *artifact*, not in the agents.

5. **Plateaus are the default.** Compounding is a thing you have to *engineer*. Skip the engineering and you will plateau — or regress when the underlying model changes and invalidates your prompts.

**Verdict:** Multi-agent advantage is largely a **one-time architectural win** that **decays or plateaus** without active maintenance, and **compounds only under disciplined scaffolding evolution** (prompt/tool/memory/eval engineering). The "compounding" is in the operator, not the system.

### 1. Academic evidence

#### 1a. The best case *for* compounding: lesson-based collaboration

**"Lessons Learned: A Multi-Agent Framework for Code LLMs to Learn and Improve"** — Liu et al., NeurIPS 2025.
https://neurips.cc/virtual/2025/poster/115952

Agents produce "lessons" (explicit knowledge extracted from successes/failures) that are banked and selectively retrieved for future tasks. A team of *small* LLMs with an accumulating lesson bank outperformed a single much larger LLM and other collaboration methods. This is the cleanest published evidence that an external memory layer can produce compounding behavior in a multi-agent system — *but note the compounding is in the bank, not the agents*. Pull the bank out, performance reverts.

**"MALT: Multi-Agent LLM Training"** — Motwani et al., ICML 2025.
https://icml.cc/virtual/2025/49342

This is actual weight updates — agents are *post-trained* on multi-agent trajectories. MALT gets 15.66% / 7.42% / 9.40% relative improvement on MATH / GSM8K / CSQA. It's real compounding, but it requires a training pipeline most deployments don't have. If you're running an inference-only parliament (like IAP), this is not your mechanism.

**"Emergent Coordination in Multi-Agent Language Models"** — Thodima 2025.
https://pages.cs.wisc.edu/~thodima/blog/2025/emergent-coordination-in-multiagent-language-models/

Uses information-theoretic measures to show that multi-agent LLM systems *can* exhibit emergence (group dynamics exceeding individual parts) and that you can *steer* it with prompts (persona, theory-of-mind instructions). Important nuance: emergence is a **property of a single run's coordination**, not a property that accumulates across runs.

#### 1b. The case *against* compounding: failure modes scale with complexity

**"Why Do Multi-Agent LLM Systems Fail?" (MAST)** — Cemri et al., arXiv 2503.13657 (March 2025).
https://arxiv.org/abs/2503.13657

Empirically cataloged **14 distinct failure modes** across 7 popular multi-agent frameworks on 200+ tasks. The failure taxonomy clusters into three categories: (1) specification/design failures, (2) inter-agent misalignment, (3) task verification failures. Key finding: **adding more agents or more conversation turns often makes things worse**, not better — more opportunities to compound errors, drift off-task, or produce confidently wrong synthesis. The failure rate does not self-correct with more runs; it requires architectural fixes.

**"Multi-Agent Design: Optimizing Agents with Better Prompts and Topologies" (MASS)** — Zhou et al., arXiv 2502.02533 (Feb 2025).

Explicitly shows that **prompt optimization dominates topology optimization** as the lever for compound-AI performance. Translation: switching from 3 agents to 5 agents, or changing the debate structure, does *less* than just rewriting the prompts. This is a load-bearing finding for anyone running a multi-agent system: the biggest improvement lever is maintenance on the prompts themselves.

**"Compound AI Systems Optimization: A Survey"** — ACL/EMNLP 2025.
https://aclanthology.org/2025.emnlp-main.1463.pdf

Surveys the field of *automated* compound-system optimization: DSPy, TextGrad, Agent Symbolic Learning, LLM-AutoDiff, LLMSelector, AFlow. Common theme: meaningful improvement requires an **outer optimization loop** (gradient-like updates to prompts, topology, or model choice) driven by a **measurable objective**. Without that loop, systems do not improve — they just run.

#### 1c. A subtle theoretical result

**"The Science of Scaling Agent Systems"** line of work (multiple 2025 papers, including LLMSelector at ICML 2025): when you scale a compound AI system, performance scales with the *quality of the weakest link* and with *how well the pipeline is tuned to the specific task*, not with raw agent count. This matches the "diminishing returns" pattern visible in every production multi-agent framework I looked at.

### 2. Industry evidence

#### 2a. TradingAgents — the headline "multi-agent works" paper

**TradingAgents (Xiao et al., arXiv 2412.20138, Dec 2024 / AAAI 2025)**
https://arxiv.org/pdf/2412.20138 · https://tradingagents-ai.github.io/

This is the most relevant direct analog to IAP: specialized LLM agents (fundamental, sentiment, technical, bull/bear researchers, risk management team, trader) debating and synthesizing. Results on AAPL/GOOGL/AMZN over a ~3-month window (Jan–Mar 2024):

| Metric | TradingAgents | Best baseline | Lift |
|---|---|---|---|
| Cumulative return (AAPL) | 26.62% | ~21% | +24.57% relative |
| Annual return (AAPL) | 30.5% | — | +28.43% |
| Sharpe (range across tickers) | 0.91–2.11 | lower | — |

**Critical caveat from the authors themselves:** Sharpe > 3 is "exceptional" and they note the period had favorable market conditions. They benchmark only 3 months due to LLM/tool-call cost (11 LLM calls + 20 tool calls *per prediction*). **No time-series of improvement is shown** — this is a "we beat baselines in a window" result, not a "we got better over time" result. The cumulative-return chart shows the system winning over the baselines in that window, not a compounding advantage curve *relative to itself*.

#### 2b. When Agents Trade — live multi-market benchmark

**"When Agents Trade: Live Multi-Market Trading Benchmark for LLM Agents"** — arXiv 2510.11695 (Oct 2025).
https://alphaxiv.org/overview/2510.11695v1

This is the more telling evidence. Four agent frameworks (DeepFundAgent, InvestorAgent, TradeAgent, HedgeFundAgent) traded four asset classes live, August–October 2025. Key findings:

- Agents had a **3-month "initialization/memory-building" window** before live trading. They *were* allowed to accumulate context.
- Results over the 2-month live window: **highly variable**. InvestorAgent + GPT-4.1 hit 40.83% on TSLA; same framework bombed on other assets. HedgeFundAgent returned 39.66% on ETH but took significant losses elsewhere.
- **Architecture mattered more than LLM backbone in some cases; reversed in others.** Inconsistent.
- **No agent showed a clean improvement trajectory within the live window.** The returns look like variance, not learning.

This is the honest industry picture: multi-agent frameworks can win, but they don't visibly *learn* on the timescale of weeks, and the variance across assets/conditions is huge.

#### 2c. Crypto portfolio management

**"LLM-Powered Multi-Agent System for Automated Crypto Portfolio Management"** — Wang et al., arXiv 2501.00826 (Jan 2025).

Similar structure, similar result: beat baselines in a window. No demonstration of an improvement curve.

#### 2d. The general industry picture

From Raschka's "State of LLMs 2025" and the compound-AI survey: **most of 2025's perceived LLM-system improvement came from tooling and inference-time scaffolding, not the models.** That's an important claim for our question. It means:

- The thing that *does* compound in practice is the operator's engineering on the scaffolding.
- Base models are effectively step-functions — you inherit an upgrade when the provider ships one, then sit flat until the next one.
- Plateaus between model upgrades are the norm. The *systems* that appear to compound are the ones whose operators are continuously shipping improvements.

### 3. Theoretical mechanisms

#### 3a. What would cause real compounding?

| Mechanism | Does it work? | Notes |
|---|---|---|
| **Weight updates (RL / fine-tuning)** | ✅ Yes, genuine learning | MALT demonstrates; requires infra + labeled trajectories. Not available to most deployments. |
| **Prompt refinement loop** | ✅ Strong, proven | DSPy, TextGrad, MASS all show prompts are the highest-leverage lever. Requires an eval set + optimizer. |
| **Lesson/memory accumulation** | ✅ Moderate, narrow | NeurIPS "Lessons Learned" shows it for code. Risk: memory becomes stale, contradictory, or polluted by failures treated as successes. |
| **Tool/data pipeline improvement** | ✅ Strong, quiet | Adding a better data source or fixing a broken tool often beats any prompt change. Underrated lever. |
| **Topology optimization** | ⚠️ Weak | MASS shows topology changes help less than prompt changes. |
| **Human feedback loops / post-mortems** | ✅ Strong if disciplined | Operator reviews errors → edits prompts/tools. This is "the system learns" but the learner is the human. |
| **Automated outer-loop optimization** | ✅ Strong | DSPy, TextGrad, AFlow. Needs a reliable objective function — which is hard for markets. |
| **Ensemble of models + model selection** | ✅ Moderate | LLMSelector shows picking different LLMs per node matters a lot. One-time gain, not compounding. |

#### 3b. What causes plateaus and regressions?

| Cause | Effect |
|---|---|
| **No learning signal** | Inference-only LLMs don't update. Without an eval loop you're literally flat. |
| **Context window limits** | Memory layers fill up, key context gets evicted, quality degrades. |
| **Prompt drift** | Operators tweaking prompts without regression tests → "improvements" that silently break other cases. |
| **Base model changes** | Provider ships a "better" model that interacts differently with your prompts. Often a regression for tuned systems until prompts are re-aligned. |
| **Error compounding across agents** | MAST's finding: more agents = more places for bad context to propagate. |
| **Survivorship bias in memory** | If the memory layer ingests the system's own outputs as "truth," confidence grows without accuracy growing. Especially dangerous in investment analysis. |
| **Regime change (for trading)** | Markets are non-stationary. A system tuned on Jan–Mar 2024 may be actively wrong in a different regime. |
| **Sycophancy compounding** | Synthesis agents tend to split differences among specialists. Over time this biases toward consensus/mediocrity unless explicitly countered. |

#### 3c. The structural difference that matters

**RL agents** update a policy from reward → next rollout is literally better-parameterized. That is compounding in the strict sense.

**LLM-based multi-agent systems** have no gradient flowing back to the parameters. Any compounding must flow through an *external artifact*: a prompt file, a memory store, a tool, an eval harness, a post-mortem document. **If none of those exist, there is no compounding.** If all of those exist and are actively maintained, you can get something that looks and behaves like compound learning.

### 4. The honest answer

#### Three kinds of "learning" to distinguish

**1. Genuine learning (weight updates).** MALT-style multi-agent post-training. Real. Rare in production. Not relevant to IAP unless you invest in a training pipeline.

**2. Apparent learning via accumulated context.** Memory buffer grows, RAG index grows, system seems smarter. This is *sometimes* real improvement (more relevant context retrieved → better decisions), but it's bounded by context-window quality and is not monotonic. It can also regress — more memory means more noise.

**3. Apparent learning via scaffolding evolution.** Operator or meta-optimizer refines prompts, tools, routing. This *is* how most production LLM systems actually improve, and it can compound indefinitely — but the learner is the engineering process, not the agents.

#### Does the distinction matter practically?

**Yes, in three specific ways:**

1. **Source of improvement = where you invest.** If improvement lives in scaffolding, invest in evals, prompt versioning, post-mortems, and tooling — not in "giving the agents more memory" or "adding more agents."

2. **Expectations / credit assignment.** If you believe the agents are learning, you'll be surprised when performance regresses after a model upgrade or after a quiet week of no operator intervention. If you know the scaffolding is the learner, you'll schedule maintenance instead of assuming the system is drifting toward superintelligence.

3. **Failure diagnosis.** When performance drops, the question "did the agents forget?" is wrong. The right questions are: did the model change? did a data source go stale? did a recent prompt edit break an old case? is the memory layer polluted? Those are all scaffolding diagnoses.

#### Where the distinction is (partly) moot

From a **product outcomes** standpoint, users don't care whether the improvement came from weights or scaffolding. They care whether tomorrow's calls are better than today's. So: the distinction matters for *how you build*, not for *whether users get value*.

But — and this is important — **systems that mistake scaffolding-learning for agent-learning tend to stagnate.** They stop investing in the thing that actually drives the curve. So even from a product standpoint, the distinction matters indirectly.

### 5. Practical implications for IAP

#### The brutal honesty layer

IAP, as an inference-only multi-agent system, **will not compound by itself.** March 2026 accuracy is a snapshot. Without deliberate engineering, by month 6 it will either:
- be at the same accuracy (best case, stable market regime, no model changes),
- be silently worse (regime change, model upgrade broke prompt assumptions, memory polluted), or
- appear to be better in cherry-picked cases while being flat on a proper eval set.

#### To make IAP actually compound, build these five things

1. **A real evaluation harness.** A held-out set of historical market windows with known outcomes where you can score IAP's decision quality (not just returns — reasoning quality, risk-flag accuracy, calibration of confidence). Without this, you cannot know if changes are improvements. This is the #1 investment. **Nothing else compounds until this exists.**

2. **Prompt versioning + regression runs.** Every prompt change is a commit. Every commit runs the eval harness. Reject commits that improve the target case but regress others. Treat prompts like code.

3. **A structured lessons / post-mortem layer** (NeurIPS "Lessons Learned" pattern). When IAP was wrong, why? Extract a structured lesson. Inject relevant lessons at decision time via retrieval. **Critical guard:** only ingest lessons tagged with ground-truth outcomes, not IAP's own conclusions. Otherwise you're training on your own hallucinations.

4. **A meta-optimizer or quarterly prompt refactor.** If you can afford DSPy/TextGrad-style automated optimization against your eval set, do it. If you can't, schedule a disciplined quarterly manual refactor — re-read every agent's prompt, re-align against what's now known about market behavior, diff against last quarter.

5. **Model-upgrade re-alignment as a routine, not an emergency.** Every time the base model changes (GPT-5.4 → next, Opus 4.7 → next), re-run the eval harness before changing anything else. Treat model upgrades as potential regressions until proven otherwise.

#### What NOT to do

- **Don't add more agents "to cover more angles."** MAST and MASS both indicate this usually hurts. Fix the prompts of the agents you have first.
- **Don't let the memory layer ingest IAP's own outputs as ground truth.** This is the path to confidently-wrong compounding. Ingest outcomes, not opinions.
- **Don't equate "ran more decisions" with "learned more."** Volume without an eval loop is not learning.
- **Don't market the system as "learning" externally** (Substack, Reddit) unless you can show the curve on a held-out eval set. "Multi-agent analysis" is defensible; "our AI is learning from the market" is a claim that will age badly.

#### Near-term concrete actions (next 2 weeks)

1. Design a 30-case historical eval set with known outcomes. Score March 2026 IAP against it. **This is your baseline.** (~1 day of work.)
2. Commit all current IAP prompts to a versioned file with a date/model stamp.
3. Add a post-decision logging layer that captures: input data, each agent's reasoning, synthesis, decision, confidence. Store raw. Later, join with realized outcomes.
4. Set a quarterly review cadence: re-run eval harness, diff against prior quarter, decide whether any drift is real or noise.
5. Before any subsequent base-model upgrade: re-run the eval harness first. Treat drops as mandatory re-alignment work, not tolerated.

If you do these five things, IAP will compound — not because the agents are learning, but because the system you're running is being *made* better on a cadence. If you skip them, you'll hit a plateau within a quarter and likely a regression within two.

### Final verdict

**Multi-agent advantage is a one-time architectural step-up, not a growth curve. Compounding is not a property of the system — it's a property of the operator.** IAP will plateau (or worse) by default. Compounding requires treating the multi-agent framework as a software product with evals, versioning, a lessons layer, and scheduled model-upgrade re-alignment. Build those, and the improvement curve is real. Skip them, and you're running a nice-looking static artifact that will eventually drift.

The distinction between "agents learning" and "scaffolding improving" matters because it tells you *where to put the work*. Put it in evals and prompts and memory-hygiene, not in adding more agents or hoping the accumulated conversation history makes things smarter.
